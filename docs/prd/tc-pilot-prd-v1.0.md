# TC Pilot — Product Requirements Document (PRD)

# **버전:** v1.0

**작성일:** 2026-03-07

**작성자:** 임도희 (웹기획자, IT그룹)

**목적:** 바이브코딩 개발 AI에게 서비스 방향성을 전달하기 위한 제품 요구사항 정의서

---

## 1. 제품 개요

### 1-1. 한 줄 정의

**TC Pilot**은 기획서 파일을 업로드하면 테스트 케이스를 자동 생성하고, 테스트 실행부터 이슈 등록까지 하나의 흐름으로 연결해주는 기획 테스트 도구이다.

### 1-2. 배경 — 왜 만드는가

웹기획자는 기획서를 작성한 후 반드시 기획 테스트(TC 작성 → 테스트 수행 → 이슈 등록)를 거친다. 현재 이 과정의 핵심 문제는 **"도구 간 단절"**이다.

현재 워크플로우는 이렇다:

1. 기획서(PPT)를 보면서 직접 TC를 작성한다. 정교성이 떨어지며 기획자 역량마다 편차가 크다.
2. 구글시트에서 테스트를 수행하며 P/F를 체크한다
3. FAIL이 발생하면 Mantis(이슈 트래커)에 가서 이슈를 **처음부터 수동으로** 작성한다
4. TC의 Steps와 기대결과를 이슈 등록 양식에 다시 복사 붙여넣기한다

이 과정에서 여러번 **복사 붙여넣기**가 발생하고, TC와 이슈 사이의 연결이 끊어지며, TC 양식이 매번 달라지고, 엣지케이스 누락이 기획자 개인 역량에 의존한다.

LLM을 직접 사용하는 것만으로는 이 문제의 **절반만 해결**된다. AI가 좋은 TC 텍스트를 만들어주지만, 넣는 문서의 질에 따라 정확도가 떨어질수있다 또 TC 생성 이후의 워크플로우(테스트 추적 → 이슈 등록 → 외부 시스템 연동)는 여전히 수동이다. **이 단절을 연결하는 것**이 TC Pilot의 존재 이유다.

### 1-3. 타겟 사용자

**주 사용자:** 웹기획자 / IT서비스 기획자 (나와 같은 역할)

- 기획서를 직접 작성하고, 기획 테스트를 수행하는 사람
- LLM을 업무에 활용하고 있지만 도구 간 연결이 비효율적이라고 느끼는 사람
- UIUX 감각은 있지만 전문 개발자는 아닌 사람

**부 사용자:** QA 엔지니어, 개발자

- 기획자가 생성한 TC와 이슈를 확인하고 대응하는 사람
- Notion 칸반보드에서 이슈 상태를 추적하는 사람

### 1-4. 해결하려는 핵심 문제 3가지

**문제 1: TC 품질의 불균일**
같은 기획자라도 피로도, 시간 압박에 따라 TC 품질이 들쭉날쭉하다. 특히 엣지케이스(권한, 빈 상태, 경계값, 동시성 등)는 체계적 점검 없이 경험에만 의존해서 누락이 빈번하다.

→ TC Pilot은 11개 엣지케이스 카테고리와 8단계 도출 프로세스를 시스템 프롬프트에 내장하여, 매번 일관된 수준의 TC를 생성한다.

**문제 2: TC ↔ 이슈 간 단절**
FAIL이 발생하면 TC에 있는 Steps, 기대결과를 이슈 트래커에 다시 수동으로 입력해야 한다. 이 과정에서 정보 유실, 중복 작성, TC-이슈 간 추적 불가 문제가 발생한다.

→ TC Pilot은 FAIL 클릭 시 해당 TC의 정보(화면코드, Steps, 기대결과)를 이슈 등록 양식에 자동으로 채워주고, 사용자는 실제결과와 심각도만 입력하면 된다.

**문제 3: 기획서 형식의 비표준화**
기획자마다 PPT 양식이 다르고, 같은 기획자도 프로젝트마다 다른 구조를 사용한다. LLM에 매번 "이런 형식의 기획서인데 TC를 만들어줘"라고 컨텍스트를 설명해야 한다.

→ TC Pilot은 파일(PPT/MD/XLSX)을 업로드하면 표준 스펙 양식으로 자동 변환하는 중간 단계를 두어, 어떤 형식의 기획서든 일관된 TC가 나오도록 한다.

## 2. 제품 요구사항

### 2-1. 핵심 사용자 플로우

전체 플로우는 5단계이며, 사용자는 이 흐름을 **순서대로** 경험한다.

```
파일 업로드 → 스펙 확인/수정 → TC 생성 → 테스트 실행(P/F) → 이슈 등록(Notion)
```

**[Step 1] 파일 업로드 & 스펙 구조화 변환**

사용자가 기획서 파일(PPT, MD, XLSX)을 드래그앤드롭하면, AI가 파일을 분석하여 아래 표준 스펙 양식으로 변환한다.

| 필드 | 설명 |
| --- | --- |
| 화면코드 | 화면 고유 식별 코드 (예: CS001) |
| 화면명칭 | 화면 이름 (예: 스케줄러 MY WORK-미처리) |
| 경로 | 네비게이션 경로 (예: 스케줄러 > MY WORK > 미처리) |
| 화면타입 | 리스트 / 폼 / 상세 / 팝업 / 대시보드 |
| 관련 권한 | 접근 가능 사용자 유형 (예: 관리자, 일반사용자, 결재자) |
| 출력조건 | 데이터 노출 조건 |
| 표시형식 | UI 표시 규칙 |
| 클릭동작 | 인터랙션 정의 |
| 비고 | 추가 참고사항 |

변환 결과는 편집 가능한 테이블로 표시되며, 사용자가 확인/수정한 후 다음 단계로 진행한다. 이 중간 정제 단계가 "기획자마다 다른 기획서 양식"을 표준화하는 핵심이다.

지원 파일 형식:

- PPT/PPTX — AI 멀티모달로 이미지+텍스트 동시 인식
- MD — 텍스트 파싱
- XLSX — 데이터 추출 후 AI 분석

**[Step 2] TC 자동 생성**

확인된 스펙을 기반으로 AI가 TC를 자동 생성한다. TC의 품질을 일정하게 유지하기 위해, AI에게 아래 규칙을 고정으로 부여한다.

TC 도출 순서 (8단계):

1. 핵심 기능 리스트업
2. 메뉴 구조 기반 분류 설정
3. 정상 시나리오(Happy Path) 먼저
4. 예외(Negative) 추가 — 정상 1개당 예외 최소 2~3개
5. 경계값 / 권한별 / 상태별 보완
6. E2E 시나리오 (해당 시)
7. 우선순위 할당
8. 누락 점검

11개 필수 점검 엣지케이스:

- 권한/인가 — 비로그인 URL 직접접근, 세션만료 후 폼제출, 계정 정지/탈퇴 상태 접근
- 빈 상태 — 목록 0건, 검색결과 0건, 초기 상태 화면, 프로필 이미지 미설정
- 동시성 — 더블클릭 방지, 동일 데이터 동시 수정 충돌
- 입력값 — XSS 스크립트, SQL Injection, 이모지, 초장문, 공백만 입력, 복사붙여넣기 서식
- 날짜/시간 — 자정 경계, 타임존(KST vs UTC), 윤년, 시작일 > 종료일
- 페이지네이션 — 0건/1건, 마지막 페이지, 정확히 페이지크기 건수, 무한스크롤 끝
- 파일 업로드 — 0바이트, 최대크기 초과, 확장자 위조, 파일명 특수문자/한글
- 경계값 — 허용 범위의 최소-1, 최소, 최대, 최대+1
- 상태 전이 — 모든 상태값의 전이 시나리오
- 필터/정렬 — 복합 조건 조합
- 표시조건 — 조건 True/False 각각

TC 품질 3원칙:

- 가독성: 한 단계에 한 동작만, 10~15단계 이내
- 재현가능성: 구체적 입력값(test@test.com), 구체적 기대결과(GNB에 닉네임 표시)
- 독립성: TC 간 상호 의존 없음

**TC 테이블 컬럼 구조:**

실무에서 사용하는 HIPAS TC 시트 양식과 ISTQB 표준을 통합한 구조이다.

| 컬럼 | 설명 | 예시 |
| --- | --- | --- |
| TC ID | {화면코드}-{관점}-{순번} | CS001-N-001 |
| 섹션 | 대분류 (VOC / 기능) | 기능 |
| 기능그룹 | 중분류 | 스케줄러 |
| 화면코드 | 화면 식별 코드 | CS001 |
| 테스트 관점 | N:정상 / E:예외 / A:권한 / R:에러 / D:데이터 | N |
| 우선순위 | P1(Critical) / P2(High) / P3(Medium) / P4(Low) | P2 |
| TC 제목 | 테스트 목적 구체적 한 문장 | 미처리 목록에서 ToDo 상태 WORK만 노출되는지 확인 |
| 사전조건 | 테스트 전 필수 상태 | 로그인 완료, ToDo 상태 WORK 1건 이상 존재 |
| 테스트 절차 | 원자적 수행 절차 | 1. 스케줄러 접속 2. MY WORK 클릭 3. 미처리 탭 확인 |
| 기대결과 | 관찰 가능한 구체적 결과 | ToDo+사용자 미완료 항목만 테이블에 노출 |
| P/F | PASS / FAIL / 진행중 / 미확인 | 미확인 |
| 이슈메모 | FAIL 시 간단한 메모 | - |

TC ID 관점 약자 정의:

- N = Normal (정상)
- E = Exception (예외)
- A = Authority (권한/인가)
- R = Error (에러 메시지)
- D = Data (데이터 정합성)

**[Step 3] 테스트 실행 & 추적**

생성된 TC 목록이 곧 테스트 체크리스트가 된다. 각 TC의 P/F 상태를 변경하면 상단 대시보드가 실시간으로 집계된다.

대시보드 표시 항목:

- 총 TC 수
- PASS 수 (초록)
- FAIL 수 (빨강)
- 진행중 수 (노랑)
- 미확인 수 (회색)
- 완료율 (PASS / 총 TC × 100%)
- 섹션별(기능그룹별) 현황

이 대시보드는 현재 실무에서 사용 중인 구글시트 진행현황 시트의 구조를 웹앱으로 옮긴 것이다.

**[Step 4] FAIL → 이슈 등록**

TC에서 FAIL을 선택하는 순간, 이슈등록 패널이 슬라이드로 열리면서 TC 데이터가 자동으로 매핑된다.

자동 매핑 규칙:

| TC 필드 | → 이슈 필드 | 처리 |
| --- | --- | --- |
| 화면코드 + TC 제목 | 이슈 제목 | 자동 |
| 테스트 절차 (Steps) | 재현 순서 | 자동 |
| 기대결과 | 기대결과 | 자동 |
| TC ID | 관련 TC | 자동 |
| — | 실제결과 | **사용자 입력** |
| — | 심각도 | **사용자 선택** |
| — | 스크린샷 | **사용자 첨부** |

사용자가 실제결과를 간단히 입력하면(예: "버튼 클릭해도 반응 없음"), AI가 TC 맥락을 참고하여 이슈 트래커에 등록하기 적합한 형식으로 재현순서와 설명을 보강한다.

심각도 체계:

| 레벨 | 기준 | 예시 |
| --- | --- | --- |
| Critical (P1) | 시스템 전체 장애, 데이터 유실 | 서버 다운, 결제 장애, 개인정보 유출 |
| Major (P2) | 핵심 기능 장애, 대안 없음 | 로그인 불가, 검색 작동 안함 |
| Minor (P3) | 일반 기능 이상, 대안 존재 | 특정 필터 오작동, 알림 미발송 |
| Low (P4) | 사소한 이슈 | 오타, 정렬 깨짐, 디자인 불일치 |

**[Step 5] Notion 이슈 DB 전송**

"등록" 버튼을 누르면 이슈가 Notion 데이터베이스에 자동으로 생성된다. TC 목록은 웹앱 내에서만 관리하고, 이슈만 Notion으로 전송한다.

Notion 이슈 DB 속성:

| 속성명 | 타입 | 용도 |
| --- | --- | --- |
| 이슈 제목 | Title | [화면코드] 이슈 요약 |
| 상태 | Select | 신규 / 확인중 / 수정중 / 해결 / 보류 |
| 심각도 | Select | Critical / Major / Minor / Low |
| 화면코드 | Text | 발생 화면 식별 |
| 재현순서 | Text | Steps |
| 기대결과 | Text | TC의 기대결과 |
| 실제결과 | Text | 사용자 입력 + AI 보강 |
| 관련TC | Text | TC ID (웹앱에서 역추적 가능) |
| 등록일 | Date | 자동 |

Notion에서는 "상태" 속성을 기준으로 칸반보드 뷰를 생성한다:
신규 → 확인중 → 수정중 → 해결 (보류는 별도 열)

### 2-2. 내보내기 요구사항

- TC 목록: xlsx 다운로드 (구글시트 호환, HIPAS 양식과 동일 구조)
- 이슈 목록: xlsx 다운로드 + Notion 자동 전송
- 대시보드: 웹앱 내 실시간 확인 (별도 내보내기 불필요)

## 3. 화면 구성

### 3-1. 전체 레이아웃

3탭 구조: 스펙 변환 | TC 목록 | 이슈 로그
상단에 프로젝트명 표시, 각 탭에서 해당 단계의 작업을 수행한다.

### 3-2. 탭 1: 스펙 변환

상단: 파일 업로드 영역 (드래그앤드롭)
하단: 변환 결과 테이블 (편집 가능)
액션: [수정] [TC 생성하기] 버튼

### 3-3. 탭 2: TC 목록 + 대시보드

상단: 진행현황 카드 (총 TC / PASS / FAIL / 진행중 / 미확인 / 완료율)
중단: 필터 (관점별 / 기능그룹별)
하단: TC 테이블 (P/F 드롭다운 포함)
액션: [xlsx 다운로드] 버튼
FAIL 선택 시: 오른쪽에서 이슈등록 슬라이드 패널이 열림

### 3-4. 이슈 등록 슬라이드 패널

TC 데이터가 자동으로 채워진 상태로 열림
사용자 입력 필드: 실제결과(텍스트), 심각도(라디오), 스크린샷(파일첨부)
액션: [AI 보강] [Notion 등록] 버튼

### 3-5. 탭 3: 이슈 로그

웹앱에서 등록한 전체 이슈 목록
Notion 전송 상태 확인 가능
필터: 심각도별, 상태별

## 4. 기술 요구사항

### 4-1. 기술 스택

| 영역 | 기술 | 이유 |
| --- | --- | --- |
| 코딩 도구 | cursor | 세미나 과제 조건 (전사 구독) |
| AI 엔진 | Gemini 3 Pro API | 멀티모달(PPT 이미지 인식), 100만 토큰 컨텍스트, JSON 모드 |
| 데이터베이스 | Supabase | TC/이슈 데이터 영구 저장, 무료 티어 |
| 외부 연동 | Notion API | 이슈 칸반보드 전송 |
| 배포 | Vercel | 기존 경험 있음, 무료 티어 |
| 파일 처리 | SheetJS (xlsx) | 엑셀 다운로드 |

### 4-2. AI 엔진 사용 포인트

TC Pilot에서 Gemini API를 호출하는 시점은 총 3곳이다:

1. **스펙 구조화 변환** — 파일 업로드 시 멀티모달 분석 → 표준 스펙 JSON 반환
2. **TC 자동 생성** — 구조화된 스펙 입력 → TC JSON 배열 반환
3. **이슈 AI 보강** — TC 맥락 + 사용자 실제결과 → 보강된 이슈 JSON 반환

3개 모두 JSON 모드로 호출하여 파싱 안정성을 확보한다.

### 4-3. 데이터 구조

**Supabase 테이블:**

projects 테이블:

- id, project_name, created_at

specs 테이블:

- id, project_id, screen_code, screen_name, path, screen_type, roles, conditions, format, interactions, notes

test_cases 테이블:

- id, project_id, spec_id, tc_id, section, feature_group, screen_code, test_perspective, priority, title, preconditions, steps, expected_result, status, issue_memo

issues 테이블:

- id, project_id, tc_id, title, severity, reproduction_steps, expected, actual, screenshot_url, notion_page_id, created_at

### 4-4. Notion 연동 범위

- 이슈 DB만 Notion에 전송 (TC는 웹앱 내에서만 관리)
- Notion API로 이슈 페이지 생성 (POST /v1/pages)
- 전송 후 Notion 페이지 URL을 웹앱의 issues 테이블에 저장하여 양방향 링크 확보

### 4-5. 미래 확장 가능성 (MVP 범위 밖)

- Mantis REST API 직접 연동 (사내 배포 시 Notion → Mantis로 엔드포인트 교체)
- 과거 TC 데이터 기반 패턴 학습 (반복 이슈 자동 제안)
- Playwright 연동 (기획서 → TC → 자동화 테스트 코드)
- Google Sheets API 연동 (TC 목록을 시트에 동기화)

## 5. 제약 조건

### 5-1. 일정

총 20시간 (4일 × 5시간)

| 일차 | 목표 |
| --- | --- |
| Day 1 | 파일 업로드 + 스펙 변환까지 작동 |

| Day 4 | xlsx 내보내기 + UI 폴리싱 + 배포 + 데모 준비 |

Day 3 종료 시점에 핵심 기능이 모두 작동해야 하며, Day 4는 폴리싱과 배포에만 집중한다.

### 5-2. 기술적 제약

- PPT 파싱 품질이 낮을 경우: MD/XLSX 우선 지원, PPT는 이미지로 변환 후 멀티모달 처리
- Gemini API 응답 지연: 로딩 인디케이터 + 스트리밍 응답 적용
- TC JSON 파싱 실패: JSON 모드 강제 + fallback 파서
- Notion API 연동 실패: xlsx 다운로드를 백업으로 유지

### 5-3. MVP 범위 결정 기준

"반드시 있어야 하는 것"과 "있으면 좋은 것"을 구분한다:

필수 (Must Have):

- 파일 업로드 → 스펙 변환 → TC 생성 → 테이블 렌더링
- P/F 체크 + 진행현황 대시보드
- FAIL → 이슈 패널 자동 매핑 → Notion 전송
- xlsx 다운로드

권장 (Should Have):

- AI 이슈 보강
- 필터 (관점별/기능그룹별)
- 이슈 로그 탭

선택 (Could Have):

- 스크린샷 첨부
- 프로젝트 관리 (다중 프로젝트)
- 테스트 이력 관리

제외 (Won't Have — 이번 MVP):

- Mantis 직접 연동
- 과거 TC 패턴 학습
- Playwright 자동화 연동
- 다국어/반응형

## 6. 성공 기준

### 6-1. 세미나 데모 시나리오 (3분)

1. 실제 기획서 PPT 파일을 드래그앤드롭한다 → 스펙이 자동 변환된다 (30초)
2. TC 생성 버튼을 누른다 → TC가 관점별로 자동 생성된다 (30초)
3. TC 3개를 PASS 체크한다 → 대시보드 수치가 변한다 (15초)
4. TC 1개를 FAIL 체크한다 → 이슈 패널이 열리고 TC 데이터가 채워져 있다 (30초)
5. 실제결과를 입력하고 Notion 등록을 누른다 (30초)
6. Notion을 열어서 칸반보드에 이슈 카드가 생긴 것을 확인한다 (15초)
7. 확장 비전 — Mantis 연동, Playwright 연동 아키텍처를 보여준다 (30초)

### 6-2. 핵심 메시지

"LLM은 좋은 TC 텍스트를 만들어주지만, TC 생성에서 테스트 추적, 이슈 등록까지 하나의 흐름으로 연결되는 건 서비스만 가능합니다. FAIL 한 번 누르면 이슈 템플릿이 자동으로 채워지고, 등록 버튼 하나로 Notion 칸반에 전달되는 경험은 ChatGPT에 텍스트를 복사 붙여넣기하는 것과 완전히 다른 차원의 효율입니다."

### 6-3. AS-IS vs TO-BE 비교

| 항목 | AS-IS (현재) | TO-BE (TC Pilot) |
| --- | --- | --- |
| TC 생성 | LLM에 프롬프트 수동 작성 | 파일 업로드 → 원클릭 생성 |
| TC 양식 | 매번 다름 | 표준 양식 고정 출력 |
| 엣지케이스 | 기획자 경험에 의존 | 11개 카테고리 자동 점검 |
| 테스트 추적 | 구글시트에 수동 입력 | 웹앱 내 P/F + 대시보드 |
| 이슈 등록 | Mantis에 수동 작성 | FAIL → 자동 매핑 → Notion 원클릭 |
| TC↔이슈 연결 | 없음 | TC ID로 양방향 추적 |
| 복사붙여넣기 | 3회 (LLM→시트→Mantis) | 0회 |
